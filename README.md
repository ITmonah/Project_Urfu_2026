# Определение заполненности площадок КГО по фотографиям

Учебный проект по дисциплине «Проектный практикум»: автоматизация определения заполненности площадок для крупногабаритных отходов (КГО) по фотографиям, которые отправляет сотрудник. Заказчик проекта — **СБЕР**. Сервис помогает оценить состояние площадки и предоставить данные для решения о необходимости вывоза отходов.

Приложение на FastAPI принимает фотографию, запускает выбранный ML-пайплайн и возвращает метку состояния и изображение с результатом. В двух режимах дополнительно рассчитывается доля площади, занятой мусором. Это оценка по двумерному изображению, а не измерение объёма отходов или физической вместимости площадки.

## Сценарий работы и результаты

1. Сотрудник фотографирует площадку и загружает фото через Web-интерфейс или `POST /api/predict`.
2. Приложение получает веса выбранного пайплайна и преобразует изображение в RGB.
3. YOLO ищет объект с именем класса `kgo_platform`.
4. Классификатор или сегментатор оценивает обнаруженную область; приложение формирует единый JSON-ответ и визуализацию.
5. Ответственный сотрудник использует результат при проверке площадки и принятии решения о вывозе. Этот организационный этап предлагается в BPMN; его автоматизация в коде отсутствует.

| Значение | Смысл | Как интерпретировать |
| --- | --- | --- |
| `kgo_empty` | Модель относит площадку к незаполненным | Не обязательно полное отсутствие мусора: для сегментации это значение ниже порога |
| `kgo_full` | Модель относит площадку к заполненным | Основание для проверки и решения ответственным сотрудником |
| `""`, `predictions: []` | Площадка не найдена или классификатор полного фото выбрал `kgo_none` | Результат отсутствует; это **не** подтверждение пустой площадки |
| `fill_percentage` | Оценка заполненности по маске | Число для SAM/SMP при наличии результата; `null` для режима классификации |

Пайплайны обрабатывают одну выбранную площадку на фотографии: режим классификации берёт первый подходящий bounding box, SAM/SMP — box с максимальной уверенностью. Поддержки полного учёта нескольких площадок в Web/API нет. Уверенность классификаторов используется внутри алгоритма, но в ответ API не передаётся.

Отдельная [MC-07: карточка всей системы](docs/model-cards.md#mc-07-система-из-трёх-пайплайнов) описывает предоставленные метрики подходов. Для каждого режима в таблице указано 235 фото; дата оценки, состав выборки и версии весов не предоставлены. Числа перенесены из [исходного снимка](docs/evaluation/pipeline-metrics-provided.png):

| Pipeline | Total | Accuracy | Macro Precision | Macro Recall | Macro F1 | Weighted F1 | No Zone | Errors |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `new_classifier_nodino` | 235 | 0.9404 | 0.9788 | 0.9295 | 0.9534 | 0.9587 | 9 | 0 |
| `sam` | 235 | 0.8000 | 0.9032 | 0.6043 | 0.6320 | 0.7648 | 5 | 0 |
| `smp` | 235 | 0.8681 | 0.8578 | 0.8066 | 0.8298 | 0.8749 | 5 | 0 |

В этом сравнении режим с двумя классификаторами имеет лучшие accuracy и macro F1, что поддерживает его текущий выбор по умолчанию. У него также больше ответов без зоны: 9/235 (**3.83%**) против 5/235 (**2.13%**) у SAM/SMP. Эти метрики относятся ко всему пайплайну и не являются показателями отдельного YOLO, EfficientNet или сегментатора. Итоговая оценка сегментационных подходов не равна качеству их масок; для этого нужны IoU/Dice.

Доступные режимы и правила принятия решения:

| Режим | Алгоритм | Выход и порог |
| --- | --- | --- |
| `new_classifier_nodino` (по умолчанию) | YOLO → кроп → EfficientNet на кропе и полном фото; выбирается ответ модели с большей максимальной softmax-оценкой, при равенстве — кроп | `kgo_empty` / `kgo_full`; `kgo_none` превращается в отсутствие результата; процент не рассчитывается |
| `sam` | YOLO → кроп с отступом 8% → SAM-декодер → TTA → очистка маски | `min(100, 100 × A_мусор / (A_пол + A_стена))`; `kgo_full` при значении **≥ 70%** |
| `smp` | YOLO → кроп → DeepLabV3+ → карта классов | `100 × A_мусор / (A_пол + A_стена + A_мусор)`; `kgo_full` при значении **≥ 50%** |

`A` — количество пикселей соответствующего класса. Формулы SAM и SMP имеют разные знаменатели, поэтому проценты и пороги нельзя напрямую сравнивать. При отсутствии пикселей площадки сегментационные функции возвращают нулевую оценку и могут сформировать `kgo_empty`; такой случай требует проверки. В SMP предусмотрен исследовательский параметр `use_floor_only`, но Web/API использует его значение `False`.

## BPMN: использование модели

![BPMN: оценка площадки КГО и решение о вывозе](docs/diagrams/model-use.png)

Диаграмма показывает общий бизнес-процесс с дорожками сотрудника, ML-сервиса и ответственного за вывоз. Ошибка обработки возвращает сотрудника к исправлению запроса. Отсутствие площадки даёт ответ без метки и ведёт к ручной оценке, а не к признанию площадки пустой. Подпроцесс оценки раскрыт в таблице режимов выше.

**Реализовано:** загрузка фото, выбор режима, получение весов, детекция, оценка, Web/JSON-ответ. **Предлагается как бизнес-процесс:** ручная проверка и решение о вывозе. Учёт заявок, отправка сообщений, интеграция с системами СБЕР и организация вывоза в репозитории не реализованы. Проверка входа на диаграмме означает декодирование фото и обработку ошибок; отдельного автоматического контроля ракурса, освещения или резкости нет.

## BPMN: переобучение модели

![BPMN: переобучение, проверка качества и выпуск модели](docs/diagrams/model-retraining.png)

[Открыть SVG](docs/diagrams/model-retraining.svg) · [Редактируемая BPMN 2.0](docs/diagrams/model-retraining.bpmn)

Это **предлагаемый процесс**, адаптированный к приложенному примеру: старт по расписанию или сигналу мониторинга → новые данные → разметка → обучение → экспертная валидация → шлюз качества → выпуск либо уведомление и журналирование → возврат к мониторингу. Для выпуска добавлены проверка сервиса и откат при неудаче. Наличие training-скриптов не означает, что этот процесс уже оркестрируется автоматически.

1. Запускать цикл при плановом пересмотре или выявленном падении качества, росте доли отсутствующих результатов, появлении новых типов площадок.
2. Собирать новые фото и проверенные ответы, удалять дубликаты, размечать `kgo_platform`, состояние площадки и маски `фон / пол / стена / мусор` для соответствующих моделей.
3. Версионировать данные; разделять train/validation/test по площадкам и сериям съёмки **до** создания кропов. Независимый test не использовать для настройки кандидата.
4. Обучать нужные компоненты, проверять кандидата и весь пайплайн на фиксированной выборке. Эксперт оценивает ошибки и качество разметки.
5. Пропускать кандидата через заранее согласованные критерии качества. Порог `AUC > 0.8` из примера не используется: он не проверяет качество масок, детектора и итогового бизнес-решения.
6. При успешной проверке выпускать новую версию весов, обновлять model cards и конфигурацию, перезапускать сервис и проверять работу. При неудаче сохранять прежнюю версию либо откатывать выпуск, регистрировать причину и возвращаться к мониторингу.

| Объект проверки | Метрики для шлюза качества | Состояние в проекте |
| --- | --- | --- |
| YOLO | mAP@50:95 и recall класса `kgo_platform` на независимых фото | В ноутбуке есть метрики, но разделение train/val требует исправления |
| Классификаторы | Macro F1, recall `kgo_full`, confusion matrix; ROC-AUC только при корректной работе со score | Расчёт бинарных метрик есть; для трёх классов AUC требует отдельного multiclass-расчёта |
| SAM / SMP | IoU/Dice класса мусора и mIoU при одинаковом протоколе оценки | Есть notebook-оценка; методики SAM и SMP различаются |
| Весь сервис | Итоговые F1/recall, доля ответов без метки, ошибок инференса и задержка | Скрипт оценки считает классификационные метрики и количество отсутствующих результатов/ошибок; мониторинг и замер задержки предлагаются |

Численные пороги приёмки не зафиксированы в репозитории и должны быть согласованы с заказчиком. Предлагаемое правило шлюза: отсутствие ухудшения относительно действующей версии по macro F1, recall `kgo_full`, доле ответов без зоны и ошибкам в пределах заранее согласованных допусков. Кандидата и baseline нужно пересчитать на одной независимой выборке и проверить срезы: освещение, сезон, тип площадки, камера и ракурс. Показатель `0.9534` из предоставленной таблицы — наблюдение на конкретной выборке, а не универсальный SLA. Согласованные пороги — условие шлюза, а не заявленные достигнутые показатели.

Автоматического scheduler, реестра экспериментов, мониторинга качества и автоматического retraining/deploy/rollback сейчас нет. GitHub Actions проверяет код и собирает Docker image, но не обучает модели. BPMN-файлы с `isExecutable="false"` служат документацией и не являются готовым workflow для исполнения. Нотация: [OMG BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2). Исходник рисунков — [generate_diagrams.py](docs/diagrams/generate_diagrams.py).

## Быстрый запуск

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r fastapi_app\requirements.txt
python -m fastapi_app.run
```

После запуска откройте `http://127.0.0.1:8000`.

HTTPS включается, если передать приложению сертификат и ключ:

```powershell
$env:KGO_SSL_CERTFILE = "C:\certs\localhost.crt"
$env:KGO_SSL_KEYFILE = "C:\certs\localhost.key"
python -m fastapi_app.run
```

В этом режиме приложение слушает HTTPS на `https://127.0.0.1:8443`, а HTTP-запросы на `http://127.0.0.1:8000` перенаправляются на HTTPS с кодом `308`.

API endpoint:

```text
POST /api/predict
```

Form-data:

- `image` - файл изображения.
- `pipeline` - один из `new_classifier_nodino`, `sam`, `smp`.

Пример запроса из PowerShell:

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/predict `
  -F "image=@C:\photos\kgo.jpg" `
  -F "pipeline=smp"
```

Основные поля ответа: `pipeline`, `label`, `bbox`, `fill_percentage`, `predictions`, `annotated_image` (PNG data URL), `checkpoints`. Bounding box в JSON заполняется только режимом SMP; SAM рисует его на фото, но не передаёт координаты в ответ. Список режимов и состояние локальных весов доступны через `GET /api/pipelines`; `GET /api/models` — совместимый альтернативный маршрут. Интерактивное описание API: `http://127.0.0.1:8000/docs`.

$env:KGO_MODEL_REPO = "likip3/AI-Models"

## Docker

Сборка образа:

```powershell
docker build -t project-urfu-2026 .
```

Запуск:

```powershell
docker run --rm -p 8000:8000 `
  -e KGO_MODEL_REPO=likip3/AI-Models `
  -e KGO_MODEL_RELEASE_TAG=v1 `
  project-urfu-2026
```

После запуска приложение доступно на `http://127.0.0.1:8000`.

Запуск Docker с HTTPS и HTTP -> HTTPS redirect:

```powershell
docker run --rm -p 8000:8000 -p 8443:8443 `
  -v C:\certs:/certs:ro `
  -e KGO_SSL_CERTFILE=/certs/localhost.crt `
  -e KGO_SSL_KEYFILE=/certs/localhost.key `
  project-urfu-2026
```

Доступные переменные:

- `KGO_SSL_CERTFILE` - путь к TLS-сертификату.
- `KGO_SSL_KEYFILE` - путь к TLS-ключу.
- `KGO_HTTPS_PORT` - HTTPS-порт, по умолчанию `8443`.
- `KGO_HTTP_PORT` - HTTP-порт для редиректа, по умолчанию `8000`.
- `KGO_HTTP_REDIRECT` - включает HTTP -> HTTPS redirect, по умолчанию `1` при наличии сертификата.
- `KGO_FORCE_HTTPS` - включает redirect middleware для запуска за reverse proxy.

В Docker image включена переменная:

```text
KGO_PRELOAD_MODEL_ASSETS=1
```

Поэтому контейнер скачивает все модельные веса в `/app/.model_cache` при старте, до начала обработки запросов.
Прогресс скачивания пишется в консоль контейнера с префиксом `[model-assets]`.

Чтобы не скачивать веса заново после каждого запуска, подключите Docker volume:

```powershell
docker run --rm -p 8000:8000 `
  -v kgo_model_cache:/app/.model_cache `
  -e KGO_MODEL_REPO=likip3/AI-Models `
  -e KGO_MODEL_RELEASE_TAG=v1 `
  project-urfu-2026
```

Для отключения preload:

```powershell
docker run --rm -p 8000:8000 `
  -e KGO_PRELOAD_MODEL_ASSETS=0 `
  project-urfu-2026
```

## Подготовка датасета и обучение

Скрипты подготовки датасета и обучения сохранены в `datasetCreation`, `NewClassificatorNoDino`, `SAM_model` и `SMP_model`.
Они не требуются для запуска Web/API приложения, но оставлены в репозитории как исследовательская и training-часть проекта.

Подготовка бинарного датасета кропов из ZIP-экспортов Datumaro и обучение классификаторов:

```powershell
python -m datasetCreation.prepare_datumaro_dataset --datasets-dir datasets
python -m datasetCreation.train_classifiers --models efficientnet_v2_s convnext_tiny
```

Архивы должны содержать изображения, bounding boxes `kgo_platform` и метки состояния `kgo_empty` / `kgo_full`. Скрипт сохраняет кропы в `datasetCreation/cropped_datumaro`, обучение — веса и метрики в `artifacts/classification`. Это отдельный экспериментальный путь; он не обновляет веса приложения автоматически.

Для трёхклассового классификатора полного фото:

```powershell
python NewClassificatorNoDino/prepareDataset.py --datasets-dir datasets --output-dir classification_data
python NewClassificatorNoDino/train_classifier.py
```

`--output-dir classification_data` нужен, чтобы согласовать выход подготовки со входом обучения. Изображения без меток состояния скрипт относит к `kgo_none`; перед обучением нужно проверить, что они действительно не содержат площадку, а не просто недоразмечены. Результат обучения требуется проверить и явно подключить как checkpoint полного фото: имя выходного файла само по себе не устанавливает его роль.

YOLO обучается в [yolo_finetune.ipynb](datasetCreation/yolo_finetune.ipynb); сегментаторы — в [SAM train_model.ipynb](SAM_model/train_model.ipynb) и [SMP train_model.ipynb](SMP_model/train_model.ipynb). Пути и преобразования данных в этих ноутбуках требуют настройки. Ограничения разбиения и соответствия рабочих весов описаны в [model cards](docs/model-cards.md).

Оценка рабочих пайплайнов на подготовленной независимой выборке Datumaro:

```powershell
python scripts/evaluate_metrics.py --dataset datasets/42 `
  --pipelines new_classifier_nodino sam smp --output reports/evaluation
```

Нужны `annotations/default.json` и `images/default/`, веса моделей и зависимости инференса; для графиков дополнительно `matplotlib`. Скрипт создаёт JSON-метрики, CSV-предсказания, сводную таблицу и графики. Фото без меток состояния пропускаются, поэтому отдельную оценку распознавания отсутствующей площадки нужно добавить. Ответы без метки и ошибки инференса учитываются как `no_zone`; они не должны исключаться из оценки итогового сервиса.
